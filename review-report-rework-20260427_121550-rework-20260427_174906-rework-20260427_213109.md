### 🟠 Important

1. **BL-001 — Stale script content persists after type change from script to panel**

   **User Story:** When a tool owner changes a tool's type from 'script' to 'panel' via meta.json and pushes the update, the system nulls out the script field to prevent stale data. However, if script.sh still exists in the tool's directory, the file-processing block re-reads it from disk and re-populates the script field, undoing the cleanup. This means the type change appears to succeed but stale script content persists on what is now a panel-type tool.

   **Impact:** The developer explicitly intended to null out the script when switching to panel type (evidenced by the code comment at line 331 and the null assignment at line 339), but this intent is silently defeated. The stale script content persists in the database. Since PanelController checks hasScript() and will execute a panel's script as an action handler, the old script-type content (designed for TOOL_* environment variables) could be invoked in a panel action context (with PANEL_ACTION, PANEL_PARAMS, PANEL_STATE variables), causing unexpected behavior or silent failures.

   **Files:**
   - `www/app/Tools/ToolPushTool.php` (lines 331–343, 350–352, 404–415)

   **Proposed Solution:** Add a `$skipScriptOnlyFiles` flag (or rename the existing flag to something generic) in the TYPE_PANEL branch at line 338-340. Then guard the script.sh file-processing block at line 405 with this flag, mirroring how template.blade.php and dependencies.json are guarded by `$skipPanelOnlyFiles`. The pattern is already established — apply it symmetrically.
