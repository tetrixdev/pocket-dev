### 🟡 Minor

1. **BL-002 — Stale-data cleanup undone by subsequent file processing during type change**

   **User Story:** When a user extracts a panel-type tool (which creates template.blade.php, script.sh, etc. on disk), then changes the type to 'script' in meta.json, and pushes back, the code first nulls blade_template to prevent stale data but then immediately re-reads template.blade.php from the directory and re-stores it on the now-script-type tool. The stale-data cleanup is silently undone by the file processing that follows it. This means the next time the user extracts this script-type tool, they will see a template.blade.php file in the output, which is confusing and perpetuates the stale data through subsequent extract-push cycles.

   **Impact:** The stale-data cleanup code (added in this PR) does not achieve its stated goal in the primary extract-push workflow. A script-type tool can end up with a non-null blade_template and panel_dependencies in the database, and a panel-type tool's script field behaves correctly only because panels legitimately use scripts. The runtime is unaffected (all queries filter by type), but tool:extract will output cross-type files, creating a confusing round-trip loop where stale data is perpetually re-stored.

   **Files:**
   - `www/app/Tools/ToolPushTool.php` (lines 319–340, 382–426)
   - `www/app/Tools/ToolExtractTool.php` (lines 119–135)

   **Proposed Solution:** When a type change is detected, skip reading files that belong exclusively to the old type during file processing. Specifically: when changing to script, skip template.blade.php and dependencies.json (these are panel-only). When changing to panel, no files need to be skipped (script.sh is valid for panels for peek/action handling). Alternatively, after file processing, re-apply the null-out for old-type-exclusive fields, or emit a warning when cross-type files are found in the directory during a type change.

### ⚪ Nitpick

1. **CONS-002 — Inconsistent error message wording between create and update paths**

   **User Story:** When an AI or user pushes a tool and the content file is empty, the error message they receive depends on whether the tool already exists. Updating an existing panel-type tool with an empty template shows 'must not be empty for panel-type tools', while creating a new panel-type tool with the same empty template shows 'must not be empty for type=panel'. The same inconsistency applies to script-type tools. This means the same validation failure produces differently worded error messages depending on whether the operation is a create or an update.

   **Impact:** Minor user confusion when the same validation error produces different phrasing depending on the code path. A developer debugging or writing tests might question whether these are the same check or different checks.

   **Files:**
   - `www/app/Tools/ToolPushTool.php` (lines 386–403, 560–576)

   **Proposed Solution:** Unify the error message wording in the create path (lines 566, 574) to match the update path's phrasing: use 'script-type tools' and 'panel-type tools' consistently in both the updateTool and createTool methods. Alternatively, adopt one consistent format like 'type=panel' in both paths.

2. **CONS-004 — ASCII box diagram misalignment in docs/README.md**

   **User Story:** When a developer views the Architecture Overview section in the documentation, the ASCII box diagram showing PHP Tool Classes has a visual misalignment. The rename from 'ToolCreate' (10 chars) to 'ToolExtract' (11 chars) on line 90 added one character without removing a trailing space. This causes the inner box right border on line 90 to be at display position 55, while the box corner characters on lines 88 and 91 are at position 54, creating a visible asymmetry in monospace rendering.

   **Impact:** The ASCII diagram renders with a visually misaligned inner box border in documentation. This is a cosmetic issue in a docs file that doesn't affect functionality but makes the documentation look less polished.

   **Files:**
   - `www/docs/README.md` (lines 88–91)

   **Proposed Solution:** Remove one trailing space from line 90 of www/docs/README.md (between 'etc.' and the closing box border '│') to bring the inner right border back to position 54, aligning it with the box corners on lines 88 and 91.
